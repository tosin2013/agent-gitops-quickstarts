# agent-gitops-quickstarts — LLM Reference

This file is the authoritative AI reference for the agent-gitops-quickstarts repository.
It is designed to give language models a complete picture of the codebase without needing to
explore the filesystem.

## Project Overview

agent-gitops-quickstarts (formerly sno-quickstarts) provides GitOps-driven Day 2 configuration
for **any OpenShift deployment** using ArgoCD + Kustomize. It is the logical continuation of:
  https://github.com/tosin2013/openshift-agent-install  (Day 1: cluster provisioning)

Supported OpenShift versions: **OCP 4.9 through 5.0** (all minor versions).

Supported platforms:
- **Bare-metal** (IPI, UPI, Assisted Installer, ZTP)
- **KVM / libvirt** (OpenShift on virtual machines)
- **VMware vSphere** (IPI and UPI)
- **Equinix Metal** (bare-metal cloud)
- **AWS** (IPI and ROSA)
- **Google Cloud Platform (GCP)**
- **Azure** (IPI and ARO)
- **Single Node OpenShift (SNO)** on any of the above platforms
- **3-node compact** and standard HA topologies

## Repository Options — Where to Host Your GitOps Repo

ArgoCD pulls manifests from a Git repository. The default points to
`https://github.com/tosin2013/sno-quickstarts.git`. Before deploying, **choose one**:

| Option | When to use | Setup |
|---|---|---|
| **GitHub (original)** | Evaluating or testing; public internet access | No setup needed |
| **GitHub fork** | Customizing; still have internet access | Fork on GitHub, then run `configure-repo.sh` |
| **Self-hosted Gitea** | Air-gapped, on-prem, or no GitHub access | Run `setup-gitea.sh` (auto-deploys Gitea on OpenShift) |
| **GitLab / Bitbucket / other** | Enterprise Git already available | Push repo there, then run `configure-repo.sh` |

### Reconfigure the repo URL (required for all non-default options)

```bash
# Dry-run first to see what would change (111 files total):
./gitops/configure-repo.sh --dry-run https://your-git-server/your-org/sno-quickstarts.git

# Apply the change:
./gitops/configure-repo.sh https://your-git-server/your-org/sno-quickstarts.git

# Then push to your repo:
git push your-remote main
```

### Deploy self-hosted Gitea on OpenShift (air-gapped / on-prem option)

```bash
# Option A — fully automated (deploy Gitea + push repo + reconfigure URLs):
./gitops/setup-gitea.sh

# Option B — manual steps:
# 1. Download and run the Gitea deployer:
curl -OL https://raw.githubusercontent.com/tosin2013/openshift-demos/master/quick-scripts/deploy-gitea.sh
chmod +x deploy-gitea.sh
./deploy-gitea.sh

# 2. After Gitea is up, reconfigure:
./gitops/configure-repo.sh https://gitea-gitea.apps.<cluster>.<domain>/<admin>/sno-quickstarts.git
```

### Add ArgoCD repo credentials (private repos)

After reconfiguring, tell ArgoCD how to authenticate:

```bash
oc create secret generic repo-creds -n openshift-gitops \
  --from-literal=username=<git-user> \
  --from-literal=password=<token-or-password> \
  --from-literal=url=<your-repo-url>
oc label secret repo-creds -n openshift-gitops argocd.argoproj.io/secret-type=repository
```

## configure-redhat-labs.sh — Multi-Node Lab Orchestrator

`gitops/configure-redhat-labs.sh` is the end-to-end Day 2 configuration script for
multi-node clusters. It orchestrates: ArgoCD bootstrap → infra node labeling →
Local Storage Operator → ODF → profile deployment.

It works on **any platform** (bare-metal, KVM, Equinix, Red Hat Labs, vSphere) and
**any node naming convention** (node names are auto-discovered or supplied via `--nodes`).

### Key flags

| Flag | Purpose |
|---|---|
| `--configure-infra-nodes` | Label worker nodes as infra/storage + patch ingress + registry |
| `--configure-storage` | Install LSO + ODF with auto-generated node overlay |
| `--nodes node1,node2,node3` | Explicit node names (default: auto-discover workers) |
| `--ocp-version 4.22` | OCP version for operator channels (default: 4.22) |
| `--odf-instance-overlay <name>` | ODF StorageCluster overlay (default: auto-select by platform) |
| `--profile <name>` | Deploy this profile non-interactively |
| `--learn` | Write execution journal → triggers self-learning |
| `--dry-run` | Preview changes without making them |

### Examples

```bash
# Dry-run preview:
./gitops/configure-redhat-labs.sh --dry-run --configure-storage --nodes worker-0,worker-1,worker-2

# Full auto-discover, self-learning:
./gitops/configure-redhat-labs.sh --configure-infra-nodes --configure-storage --profile kvm-ocp-virt --learn

# Red Hat Labs explicit:
./gitops/configure-redhat-labs.sh \
  --configure-infra-nodes --configure-storage \
  --nodes lab-worker-0,lab-worker-1,lab-worker-2 \
  --ocp-version 4.22 --learn
```

### Self-Learning System

```
configure-redhat-labs.sh --learn
        ↓
writes gitops/learnings/<timestamp>-<env_type>.yaml
        ↓
"review the latest learning at gitops/learnings/ and update skills"
        ↓
learn-environment agent (.claude/agents/learn-environment.md):
  SUCCESS → creates overlays, profiles, wrapper scripts, updates skill Known Working Configs
  FAILURE → adds failure modes to configure-lab-environment/SKILL.md
```

Over time this makes the repo smarter for every new cluster type that gets configured.

## Bootstrap Flow

```
1. oc login https://api.<cluster>.<domain>:6443    # authenticate to cluster
2. ./gitops/deploy.sh                               # bootstrap ArgoCD
   - creates namespace: openshift-gitops
   - oc create -k gitops/cluster-config/openshift-gitops
   - oc apply  -k gitops/cluster-config/openshift-gitops
3. oc apply -f gitops/apps/<profile>/cluster-config.yaml  # deploy a profile
   - Creates an ArgoCD Application pointing to gitops/cluster-config/apps/<profile>/
   - ArgoCD creates the Application-of-Apps, which creates per-operator Applications
   - Each operator Application syncs its Kustomize overlay to the cluster
```

ArgoCD runs in namespace `openshift-gitops`. The ArgoCD server is accessible via the
`openshift-gitops-server` route in that namespace.

## Kustomize Base/Overlay Pattern

Every operator directory follows this structure:

```
<operator>/
  operator/
    base/                         # Namespace, OperatorGroup, Subscription (placeholder channel)
      kustomization.yaml
      <operator>-subscription.yaml   # channel: patch-me-see-overlays-dir
      ...
    overlays/
      <channel-name>/             # e.g. stable-4.19, latest, stable-5.0
        kustomization.yaml        # resources: [../../base], patches: [patch-channel.yaml]
        patch-channel.yaml        # JSON patch: replace /spec/channel with actual value
        README.md
  instance/                       # CRD instance (StorageCluster, HyperConverged, etc.)
    base/
    overlays/
      <platform>/                 # e.g. aws, bare-metal, sno, vsphere
```

To deploy an operator at a specific OCP version: use the matching overlay path in the
ArgoCD Application's `spec.source.path`.

## ArgoCD Sync Wave Ordering

Operators that have dependencies use `argocd.argoproj.io/sync-wave` annotations:
- Wave 1: Operators (Subscription + OperatorGroup)
- Wave 2: Post-install config (console plugins, labeling jobs)
- Wave 3: Instances (StorageCluster, HyperConverged, etc.)
- Wave 4+: Applications/workloads that depend on storage/virt

## gitops-catalog — Community Operator Reference

When adding a new operator, check the community gitops-catalog first:

| Repo | Description |
|---|---|
| `redhat-cop/gitops-catalog` | Upstream: 90+ operators in base/overlay Kustomize format |
| `tosin2013/gitops-catalog` | Fork with `scripts/automate_operators.sh` and pre-dumped `operator_info.txt` |

Both follow the same base/overlay pattern as this repo. Copy the operator config locally
(don't use remote Kustomize references in production) then add platform/version overlays.

```bash
git clone --depth=1 https://github.com/tosin2013/gitops-catalog.git /tmp/catalog
ls /tmp/catalog | grep -i <operator>        # check if it's already there
grep -A10 "<operator>" /tmp/catalog/operator_info.txt  # check channels/namespaces
```

For the full workflow: see `docs/gitops-catalog.md` and the `create-kustomize-operator` skill.

## ArgoCD Sync Wave Reference

| Wave | Use for |
|---|---|
| 1 | Infrastructure operators (local-storage, CNV, Pipelines, NMState) |
| 2 | Application operators that depend on wave 1 (ODF, ACM, AAP, DevSpaces) |
| 3 | Operand instances (StorageSystem, HyperConverged CR, AAP instance, MCH) |
| 4 | Deep instances that depend on wave 3 (ODF bare-metal after LSO) |
| 5 | Deepest dependency (virt instance needing NMState + storage) |

Prune decisions: `prune: false` for storage/stateful operators, `prune: true` for stateless.

## Troubleshooting ArgoCD Sync Failures

### Check overall application status
```bash
oc get application -n openshift-gitops
oc get application -n openshift-gitops -o wide
```

### Get detailed sync error for a specific app
```bash
oc describe application <app-name> -n openshift-gitops
```

### Check ArgoCD server logs
```bash
oc logs -n openshift-gitops deployment/openshift-gitops-server | tail -50
```

### Common failure modes

1. **Subscription stuck in "UpgradePending"**
   - Cause: InstallPlan requires manual approval
   - Fix: `oc patch installplan -n <ns> <name> --type merge -p '{"spec":{"approved":true}}'`

2. **Namespace not created**
   - Cause: ArgoCD Application missing `CreateNamespace=true` syncOption
   - Fix: Add `syncOptions: [CreateNamespace=true]` to the Application spec

3. **Resource out of sync (Unknown)**
   - Cause: CRD not yet registered (operator still installing)
   - Fix: Wait for operator pod to be Running; ArgoCD will retry

4. **Permission denied syncing**
   - Cause: ArgoCD SA lacks cluster-admin
   - Fix: Verify `gitops/cluster-config/openshift-gitops/rbac.yaml` ClusterRoleBinding exists

5. **Kustomize build failure**
   - Cause: Missing base resource or overlay references deleted resource
   - Fix: Run `kustomize build <overlay-path>` locally to see exact error

6. **ODF StorageCluster stuck**
   - Cause: Insufficient nodes (ODF requires 3 nodes for Ceph, or use LVM for SNO)
   - Fix: Use `odf-lvm-operator` instead for SNO/single-node

7. **ArgoCD app stuck in Progressing**
   - Cause: Resource health check failing (e.g. Deployment not reaching desired replicas)
   - Fix: Check pod events: `oc get events -n <namespace> --sort-by=.lastTimestamp`
